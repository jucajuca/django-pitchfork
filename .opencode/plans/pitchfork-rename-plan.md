# Rename `django_pitchfork` → `pitchfork` — Plan

> **Status: DONE** (commit `f14c974`, branch `rename/pitchfork`; repo now
> located at `~/projects/DJANGO/pitchfork-engine`). Kept as the record of the
> rename. The decisions below were executed as written, with one correction:
> the repo directory is **`pitchfork-engine`**, not `pitchfork` — the local
> checkout is named after the PyPI distribution to match the sibling
> `django-haystack` convention, so `~/projects/DJANGO/` reads
> `pitchfork-engine/` + `django-haystack/`.
>
> The forward-looking half of this document (Phases 4–5) was completed by
> `docs/adr/0004-engine-name-and-package-split.md` and the naming flip in
> `.opencode/plans/haystack-replacement-plan.md`.

Rename the engine shipped by this repo from **`django-pitchfork`** to
**`pitchfork`**, and reserve **`django-pitchfork`** for the *future*
haystack-replacement API package.

This inverts the naming in `docs/adr/0002-two-packages-inverted-dependency.md`
(which today calls the engine `django-pitchfork` and the replacement
`pitchfork`). New dependency arrow, which is the natural one:

```
pitchfork-engine               this repo (import: pitchfork) —
                               Rust engine + wire + haystack backends
        ▲
django-pitchfork               future project: haystack-replacement API
                               (imports pitchfork; not built here)
```

Related:
- `docs/adr/0002-two-packages-inverted-dependency.md` — the design being superseded.
- `.opencode/plans/haystack-replacement-plan.md` — the roadmap whose naming
  this plan flips (see Phase 4).

## Naming decisions

| Concept | Before | After |
|---|---|---|
| Import package | `django_pitchfork` | **`pitchfork`** |
| PyO3 private submodule | `django_pitchfork._core` | `pitchfork._core` |
| Haystack backends | `django_pitchfork.backends.*` | `pitchfork.backends.*` |
| PyPI distribution | `django-pitchfork` | **`pitchfork-engine`** (see D1) |
| Root Cargo package | `django-pitchfork` | `pitchfork` |
| Root crate lib name | `django_pitchfork_core` | `pitchfork_py` (see R1) |
| Repo / GitHub | `jucajuca/django-pitchfork` | `jucajuca/pitchfork` (see D2) |
| Local checkout | `~/projects/DJANGO/django-pitchfork` | `~/projects/DJANGO/pitchfork-engine` (**done**) |
| Future replacement API | `pitchfork` | `django-pitchfork` |

**Unchanged on purpose** (no churn, no wire bump):

- Rust crates: `pitchfork-core`, `pitchfork-engine`, `pitchfork-server`.
- Server binary: `pitchfork-server`; wire header `X-Pitchfork-Wire`;
  `PitchforkWireV1` and `WIRE_VERSION = 1`.
- Env vars: `PITCHFORK_MODE`, `TEST_PITCHFORK_URL`, `TEST_PITCHFORK_DATA`.
- Test package `pitchfork_tests/` (already correctly named), class names
  (`PitchforkEngine`, `AutoEngine`, `PitchforkEmbeddedEngine`, …).
- Import direction inside the package: `base.py`/`server.py`/`embedded.py`
  already use relative imports, so only the directory moves.

## Phases

### Phase 0 — Decision lock (blocks the rest)

- Record decision **D1** (PyPI dist name) and **D2** (repo rename) below.
- Reserve names early if D1/D2 go ahead: create the `pitchfork-engine` PyPI
  project placeholder and rename the GitHub repo before advertising the new
  import name (the import name inside a wheel cannot be reclaimed later, but
  the *losing* window between "docs say `import pitchfork`" and "a wheel is
  published" is exactly when someone else's `pitchfork` sdist would win in a
  shared venv — see R2).

### Phase 1 — Mechanical rename (one commit, no behavior change)

Branch: `rename/pitchfork`.

```sh
git switch -c rename/pitchfork

# 1. Move the package (preserves history).
git mv python/django_pitchfork python/pitchfork

# 2. Rewrite every remaining occurrence (word-boundary safe).
rg -l 'django[_-]pitchfork' --hidden -g '!.git' -g '!Cargo.lock' -g '!.opencode/**' \
  | xargs sed -i -e 's/django_pitchfork/pitchfork/g' \
                 -e 's/django-pitchfork/pitchfork/g'

# 3. Fix the two places the blind sed gets WRONG (see R1, R3).
#    - pyproject.toml  name = "pitchfork"   -> "pitchfork-engine"
#    - Cargo.toml      [lib] name = "pitchfork_core" -> "pitchfork_py"
#    - Cargo.toml      [package] name (root) stays "pitchfork"

# 4. Regenerate the lockfile.
cargo check -q
```

Commit message: `Rename the engine package django_pitchfork -> pitchfork`
(body: no functional change; wire protocol, crates, binary, env vars unchanged).

### Phase 4 — Naming model (the part that isn't mechanical)

1. **New ADR `docs/adr/0004-engine-name-and-package-split.md`**
   - Decision: engine = `pitchfork`; haystack-replacement API =
     `django-pitchfork` (separate project, later).
   - Supersedes ADR 0002. Record *why the arrow flips*: the Django/haystack
     layer is the thing that changes with Django versions, so it should be the
     volatile top layer; the engine + wire below it stays stable. ADR 0002's
     inverted arrow was forced by the old names, not by design.
   - Record that "ENGINE paths must stay stable for existing adopters" is
     **void** (nothing published: PyPI/tags/crates.io all 404 — cite it).
   - Keep ADR 0002's one still-live constraint: the engine must not require
     haystack at runtime once the replacement exists. Under the new naming
     this becomes: *base classes move **down** into `pitchfork.backends.base`,
     and `django-pitchfork` imports them.* That is a change from ADR 0002's
     direction and must be re-verified as an ADR risk (who owns
     `BaseSearchQuery`).
2. **`docs/adr/0002-…md`**: add a `> Superseded by 0004` banner; do not
   rewrite the body (ADRs are append-only).
3. **`GLOSSARY.md`**: replace the two package terms with:
   - **Pitchfork (package)** — this repo: Rust/Tantivy engine, wire codec,
     haystack backends. Import `pitchfork`.
   - **django-pitchfork (package)** — the planned haystack-replacement API.
     *Not this repo.* Depends on `pitchfork`.
   - Add: **`pitchfork.engine`** — reserved, currently unused; `pitchfork._core`
     stays private. A stable public engine facade (`pitchfork.engine.Engine`)
     may later wrap `_core`, but do not rename `_core` in this change
     (answer to "`pitchfork` or `pitchfork.engine`?": both — package now,
     public facade later, if ever needed).
4. **`.opencode/plans/haystack-replacement-plan.md`**: flip the 10 occurrences
   so `pitchfork/` (replacement) → `django_pitchfork` … i.e. the replacement
   dir becomes `django_pitchfork/` and the wrapped engine becomes `pitchfork`.
   Also update its Phase 1 "base-class inversion (F1)" bullet and the Phase 9
   "PyPI release of `pitchfork`" bullet (→ `django-pitchfork`) and the
   Non-goals bullet ("No changes to `django_pitchfork`'s public API" →
   the engine's public API). Leave the reasoning intact; only names move.

## Decisions to confirm

- **D1 (PyPI distribution name)** — recommendation: **`pitchfork-engine`**
  (free; matches "this is the engine"; the Rust crate of the same name already
  exists in this workspace, so the story is one line).
  Alternatives: `pitchfork-search` (free, describes capability),
  `pitchfork-django` (free, but *dangerously* close to the reserved
  `django-pitchfork` and will be read as the replacement), or file a **PEP 541**
  abandoned-name request for `pitchfork` (2018, no releases, single-purpose:
  a plausible grant, but weeks of latency and no guarantee). Blocked-by:
  nothing technical — only the `[project] name` line and README install line.
- **D2 (repo rename)** — recommendation: yes, `jucajuca/pitchfork`. Optional:
  the code rename is independent of it.
- **D3 (`_core` vs `engine`)** — recommendation: keep `pitchfork._core`
  private in this change; reserve `pitchfork.engine` (documented in GLOSSARY)
  for a future public facade. Renaming it now would add churn to every
  `HAS_CORE`/import site for no user-visible gain.

## Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | Root crate `[lib] name` must not collide with `crates/pitchfork-core`'s lib (`pitchfork_core`); a blind sed produces `pitchfork_core` twice and the build fails with a duplicate crate-name error | Explicitly set `[lib] name = "pitchfork_py"`; Phase 2 gate 4 (`unzip -l`) catches any module-name/maturin mismatch |
| R2 | import name `pitchfork` is squatted on PyPI: a stray `pip install pitchfork` (or a dependency that pulls it) in a shared venv silently shadows or is shadowed by our wheel | Never rely on bare `pitchfork` in dependency specs; document `pitchfork-engine` as the install line; CI installs via `maturin develop`/explicit extras only. Optionally assert in the pytest suite that `pitchfork.__version__` is ours (Phase 2 gate 2 already does this) |
| R3 | The blind sed also rewrites the *historical* ADR 0002 body, destroying the record of why the old split existed | Exclude `docs/adr/*` from the sed; Phase 4 handles ADR 0002 as a supersede banner only |
| R4 | Stale build artifacts: `python/django_pitchfork/*.so` from an earlier `maturin develop` keeps importing under the old name and makes "it works" a lie | Delete the old directory (whole dir is `git mv`'d, so the `.so` is untracked-but-present); Phase 2 gate 3 asserts `find_spec('django_pitchfork') is None` |
| R5 | `maturin` may infer the dist name from `Cargo.toml` instead of `[project] name`, so wheel is `pitchfork` (squatted) even though pyproject says `pitchfork-engine` | Phase 2 gate 4 reads `METADATA`; if it disagrees, add `name = "pitchfork-engine"` via `[tool.maturin]`/drop the PEP 621 name and re-run before release |
| R6 | The `pitchfork-engine` dist + `pitchfork` module looks like the *replacement* to newcomers, blunting the roadmap | README + MIGRATION first paragraph state the split; GLOSSARY terms are the single wording source |
| R7 | Someone (sibling `django-haystack` checkout, notebooks, scripts outside the repo) imports `django_pitchfork` and breaks silently | Pre-flight `rg` over `~/projects` showed no external consumers on this machine; re-run before merge: `rg -l 'django_pitchfork' ~/projects -g '!**/django-pitchfork/**'` |
| R8 | Wire/doc contract drift: the "both sides in the same commit" rule mentions file paths, and paths are changing | The rule is path-agnostic in behavior; Phase 3 updates both comment sites (`wire.rs`, `wire.py`) in the same commit as the move. `WIRE_VERSION` untouched |

## Non-goals

- No wire protocol change, no `WIRE_VERSION` bump, no schema-fingerprint change.
- No rename of the Rust crates or the `pitchfork-server` binary (already right).
- No behavior, API-shape, or test-semantics change: the Python suite must pass
  unchanged in both modes.
- No `django_pitchfork` compatibility shim (nothing is released — R2/cite).
- No creation of the `django-pitchfork` replacement package; Phase 4 only
  fixes the naming in the roadmap and ADRs.
- No `pitchfork.engine` facade yet (D3).

## Rollback

Single revert of the Phase 1 commit restores the old package; nothing is
published, so there is no user-visible breakage window. Phase 5 (repo rename)
is reversible via GitHub's rename (old name returns to availability, redirects
flip) and `git remote set-url`.
